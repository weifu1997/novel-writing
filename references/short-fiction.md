# 短篇完整生产协议

本协议用于一篇内完成主要情绪或认知闭环的小说。章、节只是阅读分隔，不套用长篇卷级升级和每章追读模型。用户已给故事或旧稿时从现有材料开始，不强迫重做立项。

## 1. 锁定 Short Contract

```markdown
# Short Contract
- 交付对象 / 平台 / 文件格式：
- 总字数下限 / 上限 / 计数口径：
- 核心情绪：读完后希望留下什么感受
- 故事核：谁因为什么缺口，必须作出什么有代价的选择
- 主问题：全文结束前必须回答什么
- 读者承诺：读者持续等待的体验
- 为什么只有这个人会这样选：
- 惯例保留 / 必须改造：
- 本书私货：真实约束、人物绝不会做的事、不肯丢掉的东西
- 视角 / 人称 / 叙事时序：
- 结局边界：必须兑现、允许留白、禁止发生
- 禁止熟桥段：
- 换皮测试：删职业、城市、题材标签后故事是否仍在
- 事实不变量：改写或返修不得改变的内容
- 投稿格式：标题、小节标记、空行、引号及其他明确要求
```

用户只给目标字数时按 `SKILL.md` 的字数合约解释；默认范围必须明确告知并获准，不能从某平台经验偷偷推导。`Style Contract` 和题材模块照常使用，但短篇合同优先于长篇 profile。换皮测试未通过、或说不清为什么只有这个人会这样选时，不得开始场景大纲或正文。

## 2. 建立故事核与压力链

故事核必须同时包含人物欲望、阻力来源、关键选择和结局变化。只写“复仇”“悬疑”“治愈”是题材或情绪，不是故事核。

构造一条有限压力链：

```text
初始缺口 -> 触发事件 -> 第一次主动选择 -> 后果升级
-> 认知/关系转轴 -> 最难选择 -> 高潮结算 -> 余波
```

链条可以无反转。每一步都应由前一步产生；多个秘密、配角和支线不能回到主问题时删减或合并。先确定高潮依赖哪些前因，再决定哪些场景有资格进入正文。

## 3. 场景 / 小节大纲

小节数量服从全文长度和阅读格式，不预设六章或固定比例。每个场景使用：

```markdown
## Sxx：场景名
- 时间 / 地点 / 视角：
- 入口压力：
- 人物即时欲望：
- 阻力与升级：
- 本场景释放的信息：
- 关键选择 / 行动：
- 状态变化：风险 / 信息 / 关系 / 资源 / 决定 / 读者理解
- 与主问题的关系：
- 退出与下一场景因果：
- 预计字数：只作容量预算，不按字数强行切戏
```

预计字数总和应落入全文合约，但实际验收只认最终正文。删除某场景后下一场景仍完全成立，说明它需要合并或承担更明确的变化。

## 4. 线索、误导与揭示

有秘密、悬疑或反转时维护一张工作表：

| ID | 真相 | 首次可见证据 | 表层解释 | 谁知道 | 推进位置 | 揭示位置 | 回看是否成立 |
|---|---|---|---|---|---|---|---|

- 关键揭示依赖的证据必须提前可见，不能在高潮新增决定性事实。
- 误导利用语境、人物偏见或不完整证据；不得隐去视角人物当时明确知道并使用的事实。
- 每次揭示要重解释旧信息或改变行动，只增加一个更大的秘密不算推进。
- 反转改变因果、身份、动机、时序或读者模型；只公布新消息不是反转。
- 无反转作品用关系、报应、成长、喜剧机制或情绪兑现完成主问题，不硬加身份翻转。

## 5. 逐场景写作

写每个场景前加载 Short Contract、当前场景卡、必要前文和相关线索，不反复注入全文分析。按 [chapter-craft/scene-architecture.md](chapter-craft/scene-architecture.md) 写进入、施压、升级、转轴、选择/结算和退出；需要时再加载一张主章法卡。

场景写完立即核对批准情节点和状态变化。漏项只补计划内的动作、证据、选择或后果；已经完成职责时不靠新冲突、回忆、旁观反应和环境描写补长度。

## 6. 全文级门禁

短篇可以是一个 `正文.md`，也可以暂存为按阅读顺序排列的多个小节文件。最终版本对全部文件运行一次：

```bash
python "<skill-dir>/scripts/manuscript_guard.py" <正文或按顺序列出的小节文件> \
  --min <全文下限> --max <全文上限> --json
```

纯汉字口径追加 `--metric han_chars`；约数使用 `--target` 与 `--tolerance`。报告以所有输入文件合计值判断，不给每节套全文上下限。文件顺序属于合约；重复路径、空文件、编码错误或带外总字数都会阻断交付。

欠长时只展开已批准但呈现不足的选择、阻力、关系反应和后果；超长先删与主问题无关的支线、重复解释和无后果障碍。最多三轮针对性收口，仍带外按 `SKILL.md` 交用户裁决。

## 7. 开头、高潮、结尾与格式

- **开头**：尽快建立人物、当前缺口和异常/压力；不是必须前三句争吵，但读者应知道为什么继续。
- **高潮**：此前的证据、关系和选择汇合；关键结果归属于承担因果与代价的人。
- **结尾**：回答主问题并完成核心情绪闭环。开放结局可以保留未来未知，不能省略本篇承诺的结算。
- **格式**：正文只含故事和约定标题/小节标记。交付前检查标题、分节、空行、引号、署名和平台明确要求；没有官方当期要求时不编造固定格式。

## 8. 审稿与返修闭环

按 [review-protocol.md](review-protocol.md) 输出 findings，短篇额外检查：

- 故事核是否在开头建立并由结尾结算。
- 每个场景是否服务主问题，支线是否挤占高潮容量。
- 情绪升级是否来自得失和选择，而非重复形容。
- 线索、误导、揭示和视角信息是否公平。
- 高潮是否使用前置材料，结尾是否留下必要余波。
- 全文总字数和投稿格式是否通过。

返修先接受 findings 并锁定事实不变量；因果和线索问题先于语言问题。`suggestion` 与 `confidence: low` 默认不改。表达返修须带对照表并遵守 [review-protocol.md](review-protocol.md) 的 diff 预算。修复后重跑全文字数、线索回看、视角、格式和 `prose_lint.py`。只有原问题消失、未破坏前置证据且全文门禁通过，finding 才标为 `fixed`。
