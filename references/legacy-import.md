# 旧稿接管与基线重建

旧稿接管的目标是确认“哪些文本被接受、其中实际发生了什么、接下来从哪里继续”。原稿、作者计划、批注和模型推断必须分开；在验收完成前，旧项目仍是权威来源，staging 数据库不是正式事实源。

## 0. 锁定授权与保护原稿

先确认接管范围、是否允许整理副本、最后完整章、未完成章如何处理，以及是否迁移到结构化状态引擎。默认只读原稿，不原地改名、改编码、补章或覆盖正文。

为原稿建立只读快照或保留原位置，并记录清点报告的时间与哈希。若源文件仍在变化，停止语义提取，先由用户确定冻结版本。

## 1. 机械清点

对包含 `.md`、`.txt` 的原稿目录运行：

```bash
python "<skill-dir>/scripts/legacy_inventory.py" "<旧稿目录>" --json
```

工具只报告文件路径、UTF-8 编码状态、字节与 SHA256、文件内章节标题及行号、`visible_chars_v1`、空正文、缺章、重复章号、文件名/正文章号冲突、顺序异常和重复正文。它不判断人物、剧情、标题真伪或版本优先级。

遇到非 UTF-8 文件时保留源文件，由用户授权后在副本上转码；清点报告必须同时保留原文件哈希。重复内容、重复章号和缺章都是待裁决项，不能靠文件名自动删除或合并。

用户完成 accepted corpus 裁决后，可用清单做机械切章，仍不改正文语义：

```bash
python "<skill-dir>/scripts/legacy_inventory.py" "<旧稿目录>" \
  --accepted-manifest "<accepted.json>" --split-staging "<staging根>" --json
```

清单项需要 `path`、`sha256`、`chapter_seq` 和 `status=accepted`。合订本按标题行号切片写入 `staging/正文/第NNN章_标题.md`，并生成 `accepted-corpus.json`。哈希不符、重复章号或 staging 非空时停止。切章后仍须核对标题与番外，再对空的 staging 根运行 `story_state.py init` 并逐章 commit。

## 2. 建立 Accepted Corpus

根据清点结果建立接管清单：

```markdown
| 顺序 | 源文件 | SHA256 | 章节身份 | 接纳状态 | 备注 |
|---|---|---|---|---|---|
| 1 | ... | ... | ch-001 | accepted | 完整章 |
| 2 | ... | ... | ch-002 | excluded | 重复导出版 |
```

只允许 `accepted` 文件进入事实重建。明确最后完整章；残章可以作为工作材料保留，但其中尚未完成的变化不得提前生效。卷纲、作者便笺、删稿和提示词不属于 accepted corpus。

一个文件包含多章时，按清点报告中的标题行号在 staging 副本切成章节，并在清单记录源文件 SHA256 与起止行；不要切割或覆盖原稿。自动识别的边界仍需抽样核对，标题缺失、番外或正文中伪标题由用户裁决。

## 3. 区分证据类型

| 来源 | 可作为已发生事实 | 用法 |
|---|---|---|
| Accepted Corpus 正文 | 是 | 以精确文件、行号和短引文取证 |
| 已确认勘误 | 是 | 记录用户裁决及其覆盖范围 |
| 大纲、卷纲、人物卡 | 否 | 作为计划或待核对声明 |
| 批注、聊天记录 | 否 | 作为作者意图候选 |
| 废稿、不同版本 | 否 | 只用于冲突定位，除非重新接纳 |
| Agent 推断 | 否 | 标置信心与待确认问题 |

正文没有明确写出的心理、规则或因果，不因“看起来合理”写成确定事实。

## 4. 逆向提取候选状态

按章节顺序读取，只提取当前章新增或改变的内容：

- 人物：身份、位置、目标、身体、知识、能力、资源、关系和势力归属。
- 物品：首次出现、持有者、位置、数量、性质与状态。
- 地点与势力：存在性、层级、规则、领导和成员关系。
- 时间线：事件时序、故事时间、地点、参与者和倒叙/梦境模式。
- 线索与剧情债务：读者看到什么、谁知道什么、何时推进或回收。
- 人物弧：目标、信念、关系、身份、能力或道德选择的可见变化。
- 文风：稳定视角、叙事距离、声口、对话差异、句段节奏、意象来源和禁忌。

每项候选都带 `source_path:line`、精确短引文、首次确立章、最后确认章和置信度。找不到证据时标为 `unconfirmed`，不补写成事实。

## 5. 冲突裁决

```markdown
| ID | 冲突陈述 | 证据 A | 证据 B | 类型 | 建议裁决 | 最终裁决 |
|---|---|---|---|---|---|---|
| C001 | 年龄不一致 | 文件:行 + 引文 | 文件:行 + 引文 | 正文互斥 | 保留后文明确勘误 | pending |
```

区分真实矛盾、人物撒谎、认知变化、版本重复和名称别称。权威顺序遵循 `continuity.md`；无法从正文裁决的阻断项交给用户，不能静默选择最方便的一版。

## 6. 在 staging 重放

百万字项目或用户要求高连续性时，在独立 staging 作品根初始化 `story_state.sqlite3`。不得直接向正在使用的正式库试导入。

按 accepted corpus 的章节顺序，为每章生成正文副本、逐章记录和变更单，逐章执行 `check`、`commit`。规则如下：

- `entity_changes`、`thread_changes`、`timeline_changes` 只记录该章正文实际发生的增量。
- `references` 和 `arc_beats` 以当章原文为证据。
- 不把末章状态一次性塞进第一章，否则时间线、依赖和影响分析失真。
- 残章只在被正式接纳后提交；未接纳残章停在数据库之外。
- 原项目没有字数合约时，使用用户批准的“历史接纳合约”。可以把当章实际计数设为精确上下限以锁定导入快照，但必须注明这只表示历史版本被接纳，不代表质量达标。

轻量项目可以重建 Markdown 账本，但仍需逐章证据和同一 accepted corpus；计划超过 100 万字不得只使用 Markdown。

## 7. 验收与切换

切换前同时检查：

1. accepted 文件数量、顺序、SHA256 和总字数与清单一致。
2. 数据库章节数与 accepted corpus 一致，最后完整章一致。
3. 抽样核对卷首、卷中、卷尾和高变更章节的实体、线索与时间线证据。
4. 所有已知冲突已有裁决或明确列为未解决 blocker。
5. `story_state.py verify` 通过，工作副本等于已接受快照。
6. 生成接管报告：覆盖范围、排除内容、历史合约、未确认事实、开放剧情债务、文风契约和下一章入口。

只有验收通过并由用户接受切换后，staging 数据库才成为唯一事实源。保留原稿及清点报告，不删除源材料。
