# 长篇连续性

连续性系统的目标是提供唯一事实源，而不是积累越来越多的摘要。先识别项目已有权威文件；存在 `oh-story` 追踪状态、Story Bible、人物卡或其他账本时沿用其协议，不创建重复记录。

## 选择连续性模式

- 普通长篇可使用下方 Markdown 账本，但它依赖人工维护，不提供事务、自动冲突检查和影响传播。
- 计划超过 50 万字、超过 150 章、多人协作或要求高连续性保障时，读取 [long-project-engine.md](long-project-engine.md)，使用 `story_state.py`。
- 计划超过 100 万字时不得只用 Markdown 账本。新项目从第一章初始化结构化状态；既有项目按 [legacy-import.md](legacy-import.md) 从 accepted corpus 重建基线，或沿用原有结构化协议。
- 同一项目只能有一个已接受事实源。数据库项目的 Markdown 人物卡、章节记录和上下文卡都是工作视图，不能反向覆盖数据库。

## 新项目的最小结构

只有用户授权建立项目、现有结构无法复用且不需要结构化状态引擎时，采用：

```text
作品名/
|-- 项目.md                 # 读者承诺、篇幅、平台、视角、Style Contract
|-- 大纲/
|   |-- 总纲.md
|   |-- 第01卷_卷合同.md
|   `-- 细纲_第NNN章.md
|-- 正文/
|   `-- 第NNN章_标题.md
`-- 追踪/
    |-- 人物状态.md
    |-- 时间线.md
    |-- 活跃线索.md
    `-- 逐章记录/
        `-- 第NNN章.md
```

世界规则和势力复杂时再增加对应文件，不预建空目录和大而全模板。

## 权威顺序

1. 用户本轮明确修订的事实。
2. 已接受正文实际写出的事实。
3. 已锁定设定与追踪状态。
4. 大纲中尚未发生的计划。
5. 临时草稿和模型推断。

正文与旧设定冲突时不要偷偷覆盖。列出冲突、影响范围和最小修复方案，由用户或已有项目协议裁决。

数据库项目写前运行 `story_state.py context`。可无 ID；返回热实体、未关闭线索、近章摘要和作者/读者分栏时间线。`追踪/视图/` 下的 Markdown 是只读派生，手改不能覆盖数据库。

## 写前选择性加载

每章只加载：

- 上一章最后一个有效场景或必要的更早正文证据。
- 本章细纲与所属阶段/卷目标。
- 本章出场角色当前状态和彼此关系。
- 本章会触及的规则、地点、物品和线索。
- 近期必须兑现的承诺，以及不能提前揭露的长期信息。

角色全表、全部世界观和所有历史摘要不应每章全量注入。上下文越大越容易把计划误当事实，也越容易让语言被说明文淹没。

## 写后提交

只在最终正文通过字数、约束和文风门禁后更新。结构化项目按 `long-project-engine.md` 生成变更单并调用事务工具；以下格式仅用于轻量 Markdown 项目。每章记录应短而可验证：

```markdown
# 第 N 章
- 时间/地点：
- 已发生：只记正文明确发生的不可逆事件
- 人物变化：位置、伤势、资源、知识、关系、目标
- 新增事实：首次确立的规则、物品或背景
- 线索变化：新增 / 推进 / 误导 / 回收 / 作废
- 下一章近期债务：
- 正文文件与最终字数：
```

计划但没写出的内容不提交。推断项标注“未确认”，不可混入确定事实。

## 线索与伏笔

活跃线索至少记录：读者看见了什么、角色知道什么、真实状态（若作者已定）、最晚需要推进/回收的阶段、当前状态。不要只写“已埋伏笔”，否则续写时无法判断信息差。

伏笔不需要固定 30 章回收。按读者记忆成本和承诺强度安排：近期问题持续获得小进展，长期谜团可延后，但不能长期只重复提醒而不改变理解。

## 跨章修改

修改已接受章节前先列影响面：后续正文、人物状态、时间线、线索、章纲。修改完成后从该章向后检查依赖，不只更新被改章节的摘要。若影响范围超出用户授权，先报告而不擅自连改。

结构化项目必须先运行 `story_state.py impact`。事实变化的 revision 会自动把下游章节标记为 `needs_review`；这些章节全部 revision 或 revalidate、且 `verify` 通过前，不得继续 append。修订或复核变更单中的 `references` 与 `arc_beats` 必须描述该章当前版本的完整集合，因为提交后旧版本的依赖和人物弧不再生效。
