# 日更串行批次

日更批次用于用户明确授权一次写多章时提高连续交付效率。它是单章写作与结构化事务的编排层，不是新的事实源；数据库中的已接受章节和 `state_revision` 始终决定恢复位置。

## 适用与批次上限

- 仅在用户说日更、今天写第 N-M 章，或明确给出本章数上限（如一次写 3 章）时进入。
- 续写、接着写、继续写几章且未给章号或章数上限时，按单章处理并追问范围，不进入批次。
- 默认一批 2-3 章；用户指定更多时按其范围规划，但单次先执行最多 3 章，再交付批末报告。用户明确要求一次完成更多且环境允许时可以继续下一批，每批仍独立收尾。
- 用户只授权一章、只规划或只改细纲时不进入。
- 多章存在前后依赖，必须串行，不能并发生成正文或并发提交状态。

## 1. Batch Contract

```markdown
# Batch Contract
- 批次 ID / 日期：
- 授权章节范围：第 N-M 章
- 本次执行范围：最多前三章或用户批准值
- 各章字数合约 / 批次预估总字数：
- 所属卷 / 剧情单元 / 阶段位置：
- 批次推进目标：
- 本批允许释放的信息：
- 本批禁止提前释放的信息：
- 必须承接的近期债务 / 线索 ID：
- 停止条件：逐章确认、错误、带外字数、冲突或用户指定节点
```

总字数是容量预算；每章仍必须独立通过自己的字数合约，不能让一章超长抵消另一章欠长。

## 2. 数据库恢复点

结构化项目在开始、恢复和批末运行：

```bash
python "<skill-dir>/scripts/story_state.py" batch-status \
  --project "<作品根>" --start <N> --end <M> --json
```

- `ready`：从 `next_chapter_seq` 开始。
- `in_progress`：前缀章节已经提交，从第一章未提交处恢复；不重写或重提已完成章。
- `complete`：本批已全部接受，只做批末报告，不重复生成。
- `block`：先处理报告中的工作副本漂移、`needs_review`、卷审计、范围断层或其他 blocker。

轻量 Markdown 项目没有确定性恢复点，只适合一章一确认；需要可靠日更批次时先升级到结构化状态。聊天记录、磁盘修改时间和“我记得写到第几章”不能作为恢复依据。

## 3. 多章细纲预检

在写第一章前一次读取本批全部章纲，并逐章检查：

- 章号连续，范围与数据库 `next_chapter_seq` 一致。
- 每章有主问题、状态变化、停笔点和字数合约。
- 前章退出状态能成为后章入口；同一揭示、胜利或关系变化没有重复规划。
- 本批共同目标与当前卷合同、剧情单元和终局储备一致。
- 需要的实体、规则、线索和人物已知信息可以定点加载。
- 缺纲、互相矛盾或越过授权时先修规划，不边写边猜。

预检只确认计划可执行，不把多章未来计划写入状态库。

## 4. 串行逐章循环

对当前 `next_chapter_seq` 重复以下闭环：

1. 运行 `context`（可无 ID），读取当前 `state_revision`、热实体、未关闭线索、近三章摘要和作者/读者信息边界。冷资源再用 `--entity` / `--thread` 追加。
2. 读取上一章最终结尾、当前章纲、Style/Genre Contract 和本章主章法卡。
3. 按 `workflow.md` 的单章流程写正文。字数合约必须 `pass`。文风门禁按 Voice Pass：只删除 `placeholder-leak`、`meta-leak`、`verbatim-repeat`；其余 lint 命中写入对照表并继续提交，不把 `prose_lint.py` 非零退出当成批次失败。
4. 从最终正文生成完整变更单，执行 `check` 后立即 `commit`。
5. 再运行 `batch-status`，确认该章已进入 `completed_chapters` 且 `next_chapter_seq` 前移。
6. 只有提交成功才读取下一章；下一章必须使用更新后的状态和上一章实际结尾。

不得一次生成三章后再集中提交。否则后章会建立在未接受的临时事实上，任一前章返修都会污染整批。

## 5. 中断、失败与恢复

- 写作失败、字数带外、三种泄漏未删除、状态冲突、卷审计 blocker、`needs_review` 或用户停止时，当章不提交并立即结束批次。其余 lint blocking 不结束批次。
- 已提交章节保持有效；未提交草稿不是 accepted version，下次从 `batch-status.next_chapter_seq` 恢复。
- `check` 通过后正文又变化，必须重新 `check`；`commit` 会再次读取文件并自行复核。
- 某章 `commit` 返回卷审计 blocker 时，该章已经提交。记录批次停止原因为审计阻断，不能重复提交该章。
- 不用批次文件覆盖数据库状态，也不为凑齐批次跳过失败章。

## 6. 批末审查

逐章门禁通过后，再对本批整体检查：

- 标题没有重复、错号或与正文承诺不符。
- 相邻章入口/出口连续，时间、地点和人物已知信息无跳变。
- 情绪与压力有变化，不是连续复制同一章法。
- 本批目标获得可见推进，没有提前动用禁止信息或终局储备。
- 新增、推进、回收的剧情债务和伏笔与逐章提交一致。
- 跨章重复解释、重复冲突、重复高光和同型章尾已复核。
- 批末再次运行 `verify` 与 `batch-status`；任何正文返修都按 revision 流程处理。

## 7. 批次完成报告

```markdown
# 日更批次报告
- 完成章节：
- 各章实际字数 / 合约结果：
- 数据库 state_revision / verify：
- 批次推进目标：完成 / 部分完成 / 偏离
- 剧情债务与伏笔变化：
- 跨章审查结果：
- 停止或中断原因：
- 下一章入口与不得提前释放项：
- 剩余授权范围：
```

报告只引用已接受事实；未写成或未提交的计划明确标为候选。
