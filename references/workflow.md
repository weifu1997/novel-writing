# 创作工作流

只执行与当前请求相符的模式。规划、正文、接管、审稿和返修是不同授权，不自动串联。完整项目可以沿“立项 -> 规划 -> 写作/续写 -> 审稿 -> 返修”推进，但每轮仍服从用户指定范围。

## 1. 构思与立项

已有明确创意时从现有材料开始，不强迫用户回答固定问卷。确实缺信息时，优先确认：读者承诺、主角欲望与代价、主要阻力、篇幅/平台、叙事视角。

需要确定题材或检查题材成色时，按 [genre-craft.md](genre-craft.md) 只加载主题材模块，形成一页以内的 `Genre Contract`。它规定持续冲突、信息规则和漂移边界，不把平台套路当成剧情公式。

用户要求市场方向或商业选题时，先按 [market-scan.md](market-scan.md) 建立有日期、有来源的选题假设；需要用原文验证章法、节奏或文风时，再进入 [deconstruction-pipeline.md](deconstruction-pipeline.md)。榜单简介层信号不能直接冒充正文结构证据。

立项产物应能回答：

- 读者为什么翻开：一句具体的故事承诺，而非标签堆叠。
- 主角现在缺什么，主动追求什么，失败会失去什么。
- 核心机制如何持续制造选择，而不只是第一章噱头。
- 终局变化是什么，中途有哪些不可逆台阶。
- 题材惯例中保留什么、改造什么，避免只换人名的模板。

若用户只是讨论，直接给可比较的方案与风险，不落盘。

### 对标与原创

用户提供参考作品时，按 [comparative-analysis.md](comparative-analysis.md) 锁定决策问题、取样、建立功能矩阵并完成原创性复核。拆的是读者承诺、冲突发动、信息释放、情绪兑现、角色功能和章节因果；不复刻专名、标志性桥段、连续事件顺序、句子或独特表达。无法说明“为什么只有本书的人物会这样选择”时，说明改造还不够。

## 2. 大纲与细纲

全局大纲管承诺、因果和阶段变化；卷纲管阶段目标、升级/关系台阶和阶段结算；章纲管本章可执行的戏。

约 30-150 章或需要分卷的项目按 [volume-planning.md](volume-planning.md) 使用“全书承诺 -> 卷合同 -> 3-8 章剧情单元 -> 单章执行卡”四层规划。只把下一剧情单元展开到逐章精度；每个单元结束后，以已接受状态刷新后续计划。规划文件描述未来路线，不是已发生事实源。

章纲最小字段：

```markdown
# 第 N 章：标题
- 本章入口：人物带着什么未解决压力进入
- 本章欲望：视角人物现在要得到/避免什么
- 阻力升级：谁或什么迫使其改变办法
- 转折与选择：新信息如何造成选择，选择付出什么
- 状态变化：信息/关系/目标/风险/资源/情绪位置改变了什么
- 必发生：...
- 禁止发生：...
- 停笔点：...
- 下一章债务：读者自然会追问什么
- 字数合约：下限 / 上限 / 计数口径
```

不是每章都必须打脸、爆点或强行反转。章节至少要产生可命名的变化；钩子可以是危险、选择、答案缺口、关系偏移或阶段目标，不必都用突然来人和身份揭晓。

章纲确定主任务后，按 [chapter-craft.md](chapter-craft.md) 选择主章法卡，补齐入口状态、升级台阶、中段转轴、关键选择、结算、退出状态和章尾债务。题材模块决定冲突材料，章法模块决定组织方式；两者不得互相替代。

## 3. 单章写作

### A. Scope Lock

动笔前原样列出并内部锁定：交付对象、字数边界与计数口径、视角/人称/时态、必发生、禁止发生、时间锚、停笔点、章尾债务。它们不得被平台建议或参考模板覆盖。

### B. Context Pack

只读取“不知道就会写错”的内容：本章细纲、上一章结尾、涉及角色当前状态、相关规则、活跃线索、本书 Style Contract。不要把整本资料库塞进上下文。

### C. Scene Pass

按 [chapter-craft/scene-architecture.md](chapter-craft/scene-architecture.md) 让每场戏形成“进入 -> 施压 -> 升级 -> 转轴 -> 选择/结算 -> 退出”的因果结构；功能可以合并，不机械写成六段。再应用本章主章法卡，把最重要的篇幅留给选择、冲突和后果，过场只写到读者能定位。

### D. Prose Pass

按 `prose-craft.md` 统一视角、人物声线和叙述节奏。不要在初稿每写一句就做禁词替换；先保证一场戏完整，再处理表达层。

### E. Coverage Pass

逐项核对章纲。漏掉批准的情节点时补写该点；不要用新角色、新设定、新反转或下一章剧情补长度。

### F. Length Pass

落盘后运行本 skill 的 `scripts/chapter_guard.py`。初稿尽量瞄准范围中点，不贴上下限：

- 欠长：找“已发生但没演出来”的批准节点。补阻力的具体作用、人物选择过程、关系反应或事件后果；每段新增内容必须带来新信息或新状态。
- 超长：依次删重复结论、证据后的解释、同义心理、无后果微动作、流程性过场，再压缩不重要场景。
- 修改后总是重测；同一版本最多做 3 轮针对性收口，通过前不更新项目进度。
- 3 轮后仍欠长且批准节点已完整呈现，或仍超长且剩余内容都承担必要功能时，停止改正文并报告差额。交给用户选择：修改章纲、调整字数范围、明确接受当前长度或放弃本版；不新增未批准剧情、不注水、不破坏必要内容。

### G. Voice Pass

运行本 skill 的 `scripts/prose_lint.py`，结合通读做局部返修。关注叙述者替读者解释、所有人物同声、库存动作反复和章末预告式总结。不要为了清零报告破坏人物特有表达。初稿收口只处理确属无功能的套式句；专轮去味按第 7 节，须有对照表并遵守 diff 预算。

### H. Continuity Commit

最终正文通过所有门禁后，才把实际发生的变化写入项目账本。计划发生但正文未发生的内容不能记成事实。

结构化项目不得分别手改人物表、时间线和伏笔表。按 [long-project-engine.md](long-project-engine.md) 从最终正文提取带字数合约和原文证据的章节变更单，先 `check`，再把正文快照、逐章记录、字数结果和全局变化一起 `commit`；`commit` 会重新读取并计数，不能复用旧报告。成功前保留变更单；成功后删除临时变更单并记录 commit id。卷末提交返回审计 blocker 时，本章已经提交，不可重试同一事务；先在当前卷修订并通过新审计，引擎会在此之前阻止开启后续卷。

## 4. 旧稿接管

接管已有正文时按 [legacy-import.md](legacy-import.md) 执行：冻结原稿版本，运行 `legacy_inventory.py`，由用户裁决重复、缺章、残章和版本，形成 accepted corpus；再逐章提取带原文位置的实体、时间线、线索、人物弧和文风候选。

接管前不得把作者计划、批注、废稿或模型推断写成已发生事实。结构化项目在独立 staging 中按章节顺序生成 delta 并逐章 `check`、`commit`；数量、哈希、字数、抽样事实、时间线和 `verify` 全部验收通过后，才把新数据库指定为唯一事实源。旧稿没有原始字数合约时必须记录用户批准的历史接纳合约。

接管交付至少包含：accepted corpus 清单、排除内容、冲突裁决、最后完整章、开放剧情债务、Genre/Style Contract、基线验收结果和下一章入口。只要求评估时停在报告，不擅自迁移。

## 5. 续写

先定位最后一个已接受章节，而非最新修改时间。读取其结尾、本章章纲、相关角色状态、活跃线索和本书文风。若项目事实互相冲突，先列出冲突并按权威顺序裁决；不可悄悄选一个版本。

结构化项目先运行 `context`（可无 ID），只取热实体、未关闭线索、近三章摘要和信息边界，并以返回的 `state_revision` 构造变更单。存在 `needs_review`、未解决卷审计、派生视图漂移或其他 `verify` blocker 时先修复，不得继续生成新章掩盖旧冲突。

续写必须兑现上一章产生的近期债务，但不要求立刻结清长期谜团。承接靠具体动作、地点和未完对话，不用“上一章”“前文提到”等工程词。

## 6. 日更与多章批次

用户明确授权一次写多章时，按 [daily-batch.md](daily-batch.md) 锁定批次范围、阶段目标和信息边界，预检本批全部细纲，再严格串行执行“写一章 -> 门禁 -> `check` -> `commit` -> 刷新状态 -> 下一章”。默认每批最多三章；中断后由 `batch-status` 的数据库检查点恢复，不凭会话记忆猜进度。

逐章质量检查不能拖到批末。批末只增加标题、相邻章承接、阶段节奏、债务/伏笔和跨章重复审查，并运行 `verify`。任何未提交草稿都不计入完成章。

## 7. 改写与去 AI 味

先冻结事实边界：哪些情节、信息、伏笔、专名、视角和字数不能变。默认只改表达。闸门、对照表和 diff 预算以 [review-protocol.md](review-protocol.md) 为准；句级手法以 [prose-craft.md](prose-craft.md) 为准。

没有已接受 findings 时，先按审稿协议出报告，等用户点名 ID。用户只说“去 AI 味”且未点名 ID 时，只消费 `block` / `important` 且 `confidence` 不是 `low` 的文风项，并在改前列出 ID。`suggestion` 和 `confidence: low` 默认不改。

执行顺序：

1. 有作者样章或已确认章节时，从中提取或复核 Style Contract；平台口味不得覆盖样章。
2. 运行 `prose_lint.py`，把命中项当作候选，不做删除测试前不改。
3. 标出问题句及其功能。删掉后无损就删；说不清功能的标保留，不改。
4. 不能删的，改成视角人物此刻能感知、判断或承担后果的表达。合并同一瞬间的重复动作/情绪，不给每个情绪另配身体反应。
5. 写入对照表：`finding_id -> 原句 -> 删/改/保留 -> 改后文本或理由`。没有对照表不得改文件。
6. 只改对照表目标句及其前后各一句；禁止整章重写。无法指回 accepted ID 的 hunk 回退。
7. 复核字数与事实；去味后仍须通过原字数合约，并重跑 lint。结构化项目改旧章前跑 `impact`。
8. 不在同一轮原地宣布通过。新开只读复核，或把 diff 交给用户按 ID 核对。

修法会改情节、关系、视角或伏笔时停止去味，把该条升格为结构/事实 finding。禁止为“像人”加错字、脏话、无关口语或随机参差句长。

## 8. 审稿与返修

用户只要求审稿时不改文件。按 [review-protocol.md](review-protocol.md) 先锁定版本、覆盖范围和审查维度，再以稳定 finding ID 报告。每项 finding 都区分可验证观察、推断、影响、最小修复、不变量与置信度，引用可定位的章节/段落：

- 阻断：事实矛盾、动机断裂、视角泄漏、关键因果缺口、明确约束越界。
- 重要：场景无变化、承诺长期不兑现、人物同声、节奏在错误位置失衡。
- 建议：局部套式表达、重复解释、格式和标点问题。

先报告最影响阅读或后续写作的问题，不用总分掩盖具体证据。报告必须附 lint/字数等确定性检查结果和覆盖边界，缺附件不得称为审完。

用户授权返修后，只消费已接受 findings；`suggestion` 与 `confidence: low` 默认不改。先修事实与因果根因，再修表达；修改旧章前运行影响分析，保持 finding 中的 `invariants`。表达返修必须带对照表并遵守 diff 预算。修复后逐项回到原证据复核，并重新运行字数、连续性、lint 和必要的卷审计。超出授权的下游影响只报告，不擅自批量改写。

## 9. 短篇完整流程

短篇按 [short-fiction.md](short-fiction.md) 执行 Short Contract、故事核与压力链、场景/小节大纲、线索与反转公平性、逐场景写作、全文级字数与格式门禁，以及短篇审稿返修。短篇围绕一个核心情绪或认知变化收束；篇幅较长可以分节，但所有小节共同接受一个全文合约，不套用长篇卷级记忆或逐章日更事务。
